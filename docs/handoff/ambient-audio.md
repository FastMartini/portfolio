# Fire and snowstorm ambience

The illustrated Climb has an optional **Ambient sound** toggle. It starts off on each page visit and creates an audio context only when the visitor enables it. Starting from a user gesture follows [Web Audio autoplay guidance](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices#autoplay_policy). Keyboard and touch use the same native button and pressed state.

The campfire uses the original procedural crackles and warm low-pass noise bed, with the noise-bed gain lowered from 0.35 to 0.09 so its wind-like rushing is quieter. The crackle generator, crackle gain, and distance filter retain their original settings. The fire grows louder and brighter as the climber approaches its world position, and a small stereo pan follows its direction relative to the climber. The distance envelope is full within 120 world units and silent beyond 650, with an additional departure fade from trail position 0.12 to 0.17 so nearby switchbacks cannot bring the fire sound back at other Landmarks. The ski lodge is silent.

The snowstorm starts gently above trail position 0.48, builds to full intensity by 0.84, then fades from 0.88 to silence at 0.995. The summit is exactly silent. It retains the soft, low rushing texture approved for the snowy section: gusting procedural noise through a warm 350 Hz low-pass filter. Sound follows the rendered climb position in both directions, including when the visitor chooses static visuals with reduced motion.

`components/climb/audio/profile.ts` owns the position-to-sound mapping. `synthesis.ts` creates three fixed procedural Web Audio voices: a quiet fire bed, original fire crackles, and soft snowstorm wind. Their eight-second buffers total approximately 2.2 MiB. They run on the audio thread with no audio downloads, per-scroll buffers, nodes, or timers. Parameter ramps smooth changes, and a gain after the compressor removes residual tails when both environments are silent.

`controller.ts` handles context activity and asynchronous resume/suspend races. `AmbientSound.tsx` owns the control and optional failure feedback, fixed on the left beneath the header so a Waypoint Panel cannot cover it. Audio activity depends on Climb visibility and document visibility; panel selection does not affect it. Sound continues while a Waypoint Panel or embedded Case Study is open, and the visitor can mute or re-enable it without closing the panel. Closing a panel preserves their mute choice. List View and hidden tabs suspend playback, which resumes only if the visitor still has sound enabled. Contexts and nodes are disposed on unmount; missing or blocked audio leaves the Climb and reading controls usable. Audio never participates in scene recovery.

`tests/climb-audio.spec.ts` checks the smooth envelopes and actual output samples through native offline rendering and an analyser at the production audio output. Checks cover fire distance, snow intensity, digital silence at the summit, descent, explicit opt-in, context reuse, List View/visibility suspension, uninterrupted panel audio, pointer and keyboard access to the sound control with desktop/mobile panels open, delayed resume after mute, and unsupported or rejected audio. The audio suite runs in Chromium, Firefox, and WebKit in CI. Browser-engine tests do not constitute a physical speaker/headphone listening test.

The Linux verification job starts PulseAudio with a persistent virtual output (`module-null-sink`) before running the browser tests. This supplies the output device and audio clock needed for native Firefox playback on a headless runner. The existing opt-in, output-sample, and lifecycle assertions exercise the real audio context with the browser's normal playback policy. When reproducing these tests on headless Linux, start the same audio service and select its virtual sink before running Playwright.

A [controlled Ubuntu runner probe](https://github.com/FastMartini/portfolio/actions/runs/40343691524) reproduced the initial CI failure using only a button-triggered native oscillator: without the audio service, Firefox stayed suspended with audio time and output both zero. Starting PulseAudio and selecting the virtual sink made the identical probe run with advancing audio time and nonzero native output. The portfolio controller was not involved in that reproduction.

Compare production scrolling with and without audio using `scripts/measure-climb-scroll.mjs` and `SCROLL_SOUND=1` for the enabled run. The probe uses the real sound button and rejects a run that silently falls back to disabled audio. It also continues checking visible vectors and running decorative animation.
